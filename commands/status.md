워크트리의 커밋, 미커밋 변경, 리뷰와 터미널 상태를 조회한다.

인자: `$ARGUMENTS`. 레포 이름을 주면 해당 레포만, `--all`이면 우산과 관계없이 전체를 조회한다. `--wait`는 다음 작업이 필요할 때까지 기다린다.

우산 워크트리 안에서는 해당 우산에 속한 워크트리만 표시한다. 같은 서브 레포를 여러 우산이 사용할 수 있으므로 다른 작업을 혼동하지 않기 위해서다.

```
${CLAUDE_PLUGIN_ROOT}/bin/status.sh $ARGUMENTS
```

출력을 전달하고 다음에 필요한 작업을 한 줄로 안내한다. 판정을 추측하지 말고 카드 문구와 리뷰 칸에 표시된 내용만 전달한다.

| 표시 내용 | 다음 작업 |
|-----------|-----------|
| 커밋이 있고 리뷰가 `안 함` | `/orca:review` |
| 리뷰가 `낡음` | 수정 후 재리뷰하지 않은 상태. `/orca:review` |
| 카드에 `리뷰: blocking N건` | `/orca:handback` |
| 카드에 `리뷰 통과` | `/orca:land` |
| 터미널이 `막힘` | 사용자 입력 대기. 해당 탭에서 응답 |
| 리뷰가 `5차`로 상한에 도달 | 추가 리뷰와 land 중 선택 요청 |
| 미커밋 변경이 있고 터미널이 없음 | 에이전트 종료. 해당 워크트리 확인 |
| 소속 워크트리가 모두 머지할 준비를 마침 | 조회를 멈추고 land 여부 확인 |

## 상태 변경 대기

에이전트가 작업하는 동안 반복해서 조회하지 말고 `--wait`를 백그라운드로 실행한다.

```
${CLAUDE_PLUGIN_ROOT}/bin/status.sh --wait
```

다음 상태가 되면 표를 한 번 출력한다.

| 대기 종료 사유 | 다음 작업 |
|----------------|-----------|
| 리뷰할 워크트리가 있음 | `/orca:review` |
| 판정에 blocking이 남음 | `/orca:handback` |
| 소속 워크트리가 모두 머지할 준비를 마침 | land 여부 확인 |
| 에이전트가 사용자 입력을 기다림 | 해당 탭에서 응답 |

기본 조회 주기는 60초, 상한은 4시간이다. `WAIT_INTERVAL=`과 `WAIT_TIMEOUT=`으로 바꾼다. 대상을 구분해야 하므로 우산 워크트리 안에서만 실행한다. 대기 종료 사유와 표를 전달하고 사용자에게 확인받은 뒤 다음 단계를 실행한다.

## 머지 여부 확인

소속 서브 워크트리에 커밋이 있고, 미커밋 변경이 없고, 판정이 최신이며, blocking이 0이면 다음 안내가 나온다.

```
소속 워크트리 2개가 모두 머지할 준비가 됐다.
  진행 상황을 기록하고 land할지 사용자에게 묻는다.
```

이 안내가 나오면 폴링을 멈추고 각 워크트리의 작업을 한 줄씩 요약한 뒤 land 여부를 확인한다. 여러 레포의 계약이 연결된 변경은 머지 순서에 따라 일시적으로 계약이 깨질 수 있어 표만 보고 순서를 정하지 않는다.

일부만 준비됐다면(`3개 중 2개가 머지할 준비가 됐다`) 남은 작업의 대기 사유를 안내하고 계속 확인한다.

우산 워크트리도 별도로 확인한다. 리뷰를 거치지 않으므로 판정 파일 대신 미커밋 변경이 없는지, 기준 브랜치보다 앞서 있는지를 본다.

```
이 우산 워크트리에도 main 앞에 커밋 3개가 있다.
  land할지 사용자에게 묻는다. 이 워크트리 안에서 실행하면 삭제하지 않고 머지와 push만 한다.
```

우산에서 직접 작성한 변경도 이 안내에 따라 land 여부를 확인한다. 표 아래에는 작업 기록의 마지막 몇 줄이 표시된다. 작업 시작 시점과 리뷰 차수, 완료 이력을 확인할 수 있으므로 세션을 이어받을 때 먼저 읽는다.
